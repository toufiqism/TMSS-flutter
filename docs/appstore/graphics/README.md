# Store graphics — App Store

The iOS counterpart of `../../play/graphics/README.md`. Same principle: everything the
store asks for as an image is generated from the repo, so a re-run reproduces the files.
The release procedure these feed into is `../README.md`.

| File | Spec | Generated by |
|---|---|---|
| `screenshots/6.9-inch/*.png` | six 1320×2868 frames | `tool/store/generate_ios_store_screenshots.py` |
| `screenshots/6.5-inch/*.png` | the same six at 1284×2778 | same script, same run |
| `screenshots/raw/*.png` | 1320×2868 simulator captures | `tool/store/capture_ios_screenshots.sh` |

```bash
./tool/store/capture_ios_screenshots.sh              # raws, from the simulator
python3 tool/store/generate_ios_store_screenshots.py # framed, ready to upload
```

Requires `pip3 install pillow`. Unlike the Play graphics there is no `resvg` step, because
there is nothing here to rasterise from SVG — see "What the App Store does not want".

## What the App Store does not want

Three of the four Play assets have no slot on the App Store, so they are not generated
here and their absence is deliberate:

| Play asset | Why there is no iOS equivalent |
|---|---|
| `play-icon-512.png` | The icon is read out of the binary — `ios/Runner/Assets.xcassets/AppIcon.appiconset/Icon-App-1024x1024@1x.png`, already 1024×1024 and already opaque. Nothing is uploaded separately, and App Store Connect rejects an icon with an alpha channel. |
| `play-feature-1024x500.png` | The App Store has no feature graphic, banner or header image anywhere in a product page. Screenshots carry the whole listing. |
| `youtube-thumbnail-1280x720.png` | No YouTube dependency: iOS has App Previews instead, played inline on the product page. |

## App Previews are not generated, on purpose

`tool/store/generate_promo_video.py` builds the Play promo video by animating the raw
captures — an intro card, six push-ins, an outro. That is fine for YouTube and would be
rejected here. App Store Review guideline 2.3.3 requires an App Preview to be *captured
on device*, showing the app actually running; a slideshow of stills assembled by a script
is exactly what the rule excludes.

If a preview is wanted later it has to be a screen recording — `xcrun simctl io <udid>
recordVideo` on the simulator, or QuickTime against a real iPhone — trimmed to 15–30 s.
It is optional, and the listing is complete without one.

## The screenshots contain no real data

Identical constraint to Play, and stricter in effect because an App Store listing is
public the moment the app is approved. Every name, address, vehicle plate, phone number
and requisition in `screenshots/raw/` is invented: the captures are of the real app
talking to `tool/store/mock_api_server.py`, which serves twelve synthetic requisitions and
a four-person employee directory.

The live account holds a real employee's name, ID and phone number and real business
records, none of which may be published to a store listing; it is also full of
`Probe Test` rows left over from API contract probing, which would make the listing look
broken. Capturing against the mock solves both at once, and needs no reviewer account
provisioned in production first.

## Recapturing the raw frames

Wanted whenever the UI changes.

```bash
./tool/store/capture_ios_screenshots.sh                    # iPhone 17 Pro Max
./tool/store/capture_ios_screenshots.sh "iPhone 16 Pro Max"
```

The script starts the mock server, boots the simulator, freezes the status bar at 9:41
with full bars and a charged battery, resets the text size to default, and runs the
capture. It stops the mock again on the way out, including on Ctrl-C.

### Why the app drives itself

The Android pipeline walks the UI with `adb shell input tap`. **There is no iOS
equivalent on this machine**: `idb` is not installed, `osascript` is refused assistive
access, and `xcrun simctl` exposes only `io`, `ui`, `keychain` and `pbcopy` — no input
verbs at all. So navigation happens from inside the app instead:

- `integration_test/store_screenshots_test.dart` pumps the real `TracGoApp`, signs in
  against the mock by entering text and tapping through the test binding, then reaches
  the remaining screens with `GoRouter.go` rather than by tapping. Every capture is
  gated on a string that only appears once that screen has rendered, so a slow response
  fails the run instead of quietly producing a second copy of the previous screen.
- `test_driver/store_screenshots_test.dart` receives the bytes and writes them to
  `screenshots/raw/`.

This is why `integration_test` is in `pubspec.yaml`'s dev dependencies; nothing else uses
it yet.

### Debug build, unlike Android

The Play README insists on a profile build, because the main Android manifest sets
`usesCleartextTraffic="false"` and only the debug and profile manifests override it — a
release build simply cannot reach the mock over `http://`.

None of that applies here, for two separate reasons:

1. **Flutter cannot build profile or release for the iOS Simulator.** Debug is the only
   option, and for a pure-Flutter UI it rasterises identically to release.
2. **App Transport Security never sees these requests.** ATS governs `URLSession` and
   `CFNetwork`; Dart's `HttpClient` — which Dio sits on — is its own socket-level stack.
   So `http://127.0.0.1:8099` works with no `NSAppTransportSecurity` exception, and none
   has been added to `ios/Runner/Info.plist`. Do not add one "to make the mock work":
   it would ship, and it is not what is making it work.

### Framing

`generate_ios_store_screenshots.py` composes each raw onto a page-coloured canvas, with a
headline, a lime rule and the device shot inset and bled off the bottom. Captions are the
same six as the Play set, deliberately — the listing copy was written and reviewed once.

Unlike Play, the framing is not technically required: App Store Connect wants one of a
fixed set of exact sizes, and the 6.9" simulator already produces one (1320×2868).

### Two sets, because ASC enforces sizes per tab

App Store Connect has a tab per display size, each accepting only its own dimensions, and
it refuses the whole batch on the first file that does not match — reported as *"The
dimensions of one or more screenshots are wrong"* with the accepted list for **that tab**.
Dropping the 6.9" files on the 6.5" tab produces exactly that error, and the fault is the
tab, not the capture.

| Slot | Accepted | Composed at |
|---|---|---|
| iPhone 6.9" Display | 1320×2868, 1290×2796 | **1320×2868** — the raw's own size |
| iPhone 6.5" Display | 1284×2778, 1242×2688 | **1284×2778** — device shot scaled into a shorter canvas |

**6.9" alone satisfies a submission**; Apple scales it down for every smaller device. The
6.5" set exists only so that clicking the other tab is not a dead end. Nothing is
recaptured for it — the canvas aspect ratios differ by 0.4%, far too little to distort
anything.

## Uploading

App Store Connect → the app → the version → **App Previews and Screenshots**. Select the
tab first, then upload the matching directory — **the tab decides which sizes are legal**:

| Tab | Upload |
|---|---|
| iPhone 6.9" Display | `screenshots/6.9-inch/` |
| iPhone 6.5" Display | `screenshots/6.5-inch/` |

The 6.9" tab alone is all that is required now the app is iPhone-only
(`TARGETED_DEVICE_FAMILY = 1`); Apple scales that set down for smaller devices, and there
is no iPad tab because the app does not claim iPad support. Uploading the 6.9" files to
the 6.5" tab fails with *"The dimensions of one or more screenshots are wrong"* — the
listed sizes in that message describe the tab you are on, not a problem with the files.

Listing copy, reviewer credentials and the privacy questionnaire are not here — see
`../../play/store-listing.md`, `../../play/app-access.md` and `../../play/data-safety.md`,
whose content transfers with only the wording changes each store's fields force.
